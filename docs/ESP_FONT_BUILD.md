# ESP32-S3 font initialization and terminal rendering build report

本页保存早期字体渲染构建证据，镜像大小与布局数值属于当时版本。2026-09-16 的更新安全实现见 `ESP_OTA_V2.md`：字体初始化失败已改为试运行复位或已确认镜像的 USB 维护模式，不再仅记录警告后继续正常启动。下文栅格化、字体内容与历史测试结果保留，不作为当前候选已部署的证明。

## Scope and implemented changes

This follow-up supersedes the initialization/clipping concerns in the earlier `FONT_BUILD.md` report for the application built here. No keyboard source, hardware wiring, original repository, SSH session or flash contents were changed by this work.

- `firmware/esp32s3/main/main.c`: calls `ttf_font_init()` before `mix_ui_init()`. Font failure is logged and startup continues into the existing ASCII fallback; a missing font does not prevent the local UI from starting.
- `firmware/esp32s3/main/ttf_font.c` / `.h`: add `ttf_draw_cell()` and idempotent `ttf_font_deinit()`. Successful repeated init does not remap or reallocate. Failed initialization releases cache, face, FreeType library and partition mapping in reverse ownership order, allowing a retry. Raw sfnt signature, scalable outline and Unicode charmap checks reject unsupported font input.
- `firmware/esp32s3/main/mix_ui.c`: terminal cells directly use `ttf_draw_cell()` instead of rendering into a 32×24 scratch buffer and cropping to advance width. The unused codepoint-to-UTF-8 conversion helper was removed. UI strings, 80×28 geometry, 12×24/24×24 cell allocation and cursor coordinates remain unchanged.

## Rendering behavior

The requested 20 px face's ascent/descent establish one shared terminal baseline. The font's line extent is fitted into 24 px without a MiSans-specific vertical offset; shorter line extents are centered without enlarging them. Glyphs extending beyond the font's nominal ascent or descent fit into the corresponding side of that same baseline rather than moving the baseline per character.

Horizontal fitting includes both the logical advance and actual bitmap bounds (`bitmap_left` through `bitmap_left + bitmap.width`), including negative left bearings and bold expansion. This prevents the old loss of `j`'s left edge and the right edges of wide proportional glyphs. Max-alpha area sampling retains thin source strokes during downscaling; it can make small text slightly heavier than ordinary grayscale interpolation. Bold expansion stays inside the same cell. Every store is bounded by both the cell and framebuffer.

Cached-glyph lookup now also restores the requested FreeType size on cache hits. This avoids stale face metrics after another UI label uses a different size.

## Reproducible local test commands

The vendored FreeType version used by the firmware and native harness is **2.14.3**. This is separate from the earlier Pillow engine (FreeType 2.13.3). Native tests compile the actual production `ttf_font.c`, not a Python reimplementation, with WSL GCC, `-Wall -Wextra -Werror`, AddressSanitizer and UndefinedBehaviorSanitizer. ESP allocation and partition functions are narrowly stubbed; FreeType rasterization is real.

Build the local native dependency from the project root in WSL:

```text
cmake -S firmware/esp32s3/managed_components/espressif__freetype/freetype -B build/host-freetype -DFT_DISABLE_ZLIB=ON -DFT_DISABLE_BZIP2=ON -DFT_DISABLE_PNG=ON -DFT_DISABLE_HARFBUZZ=ON -DFT_DISABLE_BROTLI=ON -DCMAKE_BUILD_TYPE=Debug
cmake --build build/host-freetype -j4
```

Then run on Windows using the Python 3.12 installation with fontTools:

```text
python -m unittest discover -s tests -p test_ttf_render.py -v
```

Set `MIXOS_TEST_RENDER_FONT` to the generated `build/font/MiSans-Normal-gb2312.ttf` to also run the real-font case. The ordinary case creates a synthetic TTF with negative bearing, outline wider than advance, and descenders exceeding the nominal font metrics; it does not require the user's original font.

All three tests passed with the real-font case enabled:

- Fault injection at partition lookup, mmap, FreeType library creation, face creation, charmap selection and cache allocation; malformed/empty partitions, invalid partition size, retry after failure, repeated init/deinit, glyph allocation failure and retry.
- 12 px and 24 px cells, normal and bold, interior and partially off-screen coordinates, guard bytes around the framebuffer and sentinels outside each cell, blank glyphs and invalid sizes.
- Same baseline above/below checks for `g j p q y`; cache metrics after switching from 20 px to 64 px and back.
- Every nonzero source bitmap pixel for `% X Y _ g j p q r y 中 文` was isolated and verified to survive cell fitting: **2,046 real MiSans pixel checks** and **9,504 synthetic pixel checks**, across both cell widths. No sanitizer report or outside-cell write occurred.
- Source integration check confirms font initialization occurs before UI initialization and the old scratch renderer is absent.

Existing `test_build_font.py` also passed again with real-font integration enabled (**26/26**). The existing UI regression fixtures were minimally adapted to the new cell API (`tests/test_preview_ui.py` and `tests/test_preview_ui_host.c`); all **4/4** tests passed, including 40 theme/language/page combinations, dirty rows, CJK cells, local confirmation and framebuffer guards. Together with the three new renderer tests, **33 relevant tests passed**.

The real font was rebuilt to refresh the changed `mix_ui.c` source hash in the manifest; there are no new UI strings, coverage remains complete, and the TTF bytes/hash remain unchanged:

## ESP-IDF environment

Use `python tests/esp_font_build.py build` from Windows. It preserves the recovery app, invokes only a local WSL ESP-IDF build and writes a report. The helper uses the existing project-local ESP-IDF 5.4.2 tree, Python 3.10 IDF virtual environment and Xtensa GCC 14.2.0 toolchain. Full `export.sh` activation requires an uninstalled RISC-V debugger unrelated to this ESP32-S3 build, so the helper sets the required local paths explicitly instead of downloading or modifying the tool installation. It does not flash.

## Remaining limits

These checks validate production rendering logic and target compilation, not LCD appearance, target FreeType timing or PSRAM behavior under a full live session. The terminal still has the existing restricted combining-character/emoji/Unicode width handling. Font coverage remains the earlier documented subset (including the explicitly recorded U+FFFD → `?` fallback and missing optional U+30FB). The app and font must both match the intended release before deployment. No device deployment or live framebuffer capture was performed here.
