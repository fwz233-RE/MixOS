## 更新对象

A/B 是 ESP32-S3 应用槽，不是 Linux 系统分区。Linux CM5 通过内部 USB Host → CDC 发起操作。`ota_0=0x10000/0x1f0000`，`ota_1=0x610000/0x1f0000`；分区表、bootloader、字体和 phy 保持原位。NVS 设置保留，事务记录使用独立 `mix_ota` 命名空间。

普通更新只擦写非运行应用槽，随后通过 IDF 更新 otadata。两个应用槽不能同时承担永久固定恢复镜像和无限交替升级：首次 B 槽确认可用后，必须显式批准解除 A 槽基线保护。

## 固件保障

- PSRAM 指令／只读数据执行保留，LCD RGB/GDMA 的 cache-off 中断标志关闭，避免缓存关闭时 RGB bounce 中断读 PSRAM。保留原有双帧缓冲、bounce、分辨率和时序。此修改针对已确认可达风险，不能据此认定历史故障根因已捕获。
- panic 后自动重启；应用在 ESP-IDF 5.4.2 的 CPU0／CORE 优先级 0 初始化钩子中接管 RTC 看门狗，建立一次名义 30 秒预算，`app_main` 不再续期。MAIN、IO、OTA 任务都实际报告本地进度且 USB 就绪后，才交接给任务看门狗；定时器不能代替卡住任务喂狗。IDF 的 `esp_clk_init()` 在此钩子之前本来就会喂狗并按应用配置重设超时，但这些应用代码都不能延长旧 bootloader 自身镜像加载及更早初始化所受的名义 9 秒预算。源码顺序和主机测试不代替最终 ELF 与实机时序验证。
- 单一 OTA 工作任务拥有 flash 句柄、最终校验、启动选择、NVS 日志和确认；UI／USB 不执行这些 flash 操作。
- 试运行要求整帧提交、扫描进度、本地任务进度、USB 就绪和实际协议往返。只有 IDF 标记成功并复查 VALID，才解除待确认保护。Linux 缺席本身不是本地故障。
- 初始化失败的候选自动复位，让 bootloader 回滚；已 VALID 版本可进入最小 USB 维护路径，不依赖屏幕／字体／音频硬件。USB 栈自身失效或硬件损坏仍可能使维护不可用。
- QUERY 无副作用；END 与新版 REBOOT 分开。重复 END 不再次消费句柄或再次提交；旧 REBOOT 不能重启新一轮试运行。协议见 `protocol/OTA_V2.md`。
- 文件 SHA 是精确 app.bin 字节，不等于 ELF SHA 或填满整个分区后的 SHA。收尾同时保留 IDF 镜像校验和 flash 精确文件读回。

RTC 记录只辅助诊断，不跨断电保证保留。构建报告保存 RTC 符号地址；跨版本地址变化会丢失诊断历史，不能把 RTC 当作启动授权或唯一事务事实。NVS 事务与 otadata 不能原子提交，重启后使用实际启动选择和镜像内容对账。

## Linux 本机入口

源代码入口 `linux/mixos-esp-update` 调用 `tools/mixos_esp_update.py`。本机支持 `inspect`、`package`、`apply`、`status`。发布包至少包含 `app.bin` 和 `manifest.json`；打包后带标准库运行器，不需要 Windows、SSH 或源码树。

- 本地 `inspect --package ...` 和 `apply --package ... --dry-run` 只检查文件，不接触端口、服务或网络。
- `inspect --live` 明确打开设备并协调服务所有权，属于需要授权的设备操作。
- `apply --package ...` 是实际更新授权，提交独立 systemd 用户任务；`--wait` 等待同一任务结果。
- `status --job ...` 查询已有任务；`apply --resume ...` 仅观察／完成既有事务，不恢复接收或重新上传镜像。
- `--allow-replace-baseline` 是解除旧 A 槽保护的额外授权；还需明确的、完整哈希绑定的已验证 B 槽发布包，不能根据设备自报的任意哈希解除保护。
- 普通入口默认要求新版能力，沉默不会自动降级为旧 OTA，也不会触发分区迁移。`deploy_ota.py` 是调用同一入口的可选 SSH 包装器。

Linux 安装需要普通用户有串口权限、受控的 `mixosd.service` stop/start 权限、持久用户服务运行条件及共享锁目录。`tools/install_ota_policy.py --user pi` 只输出供管理员独立批准和执行的配置命令，本身不安装或授予权限。该脚本不部署首次安装所需的受信任监管进程与审批包。本轮没有把这些权限或服务应用到设备，更新工作进程始终使用普通用户。

本地任务先持久记录，再停服务并核实，最后打开串口。串口启用 DTR 前核对实时 sysfs 的 `303a:80c3`、厂商／产品描述、序列号和 CDC 接口号；软件／按钮 ROM 身份不能仅凭相似名称通过检查，工具不会发送 RTS 复位序列。更新结束关闭端口并恢复原服务状态。结果分别保存固件、服务和证据持久化状态；退出码 0 只表示全部成功，排队／执行中不是成功。节点出现、100% ACK、服务 active 都不足以证明更新完成。

## 发布包构建

`tests/esp_font_build.py build` 运行本地 ESP-IDF 构建并生成报告。新报告覆盖全部 main 源码／头文件、构建配置与依赖锁、生成配置、ELF 和分区表哈希；编译前后的输入须保持一致，成功产物另存 `completed-build.json` 绑定证据。`report` 不能为旧二进制重新绑定修改后的源码。

`tools/esp_release.py --output <新目录>` 检查该报告与当前文件逐字节一致，再产生便携包。修改任一 OTA 源码、配置、布局或旧报告遗漏新文件都会拒绝打包；不能手工修改报告 hash 绕过检查。有效安全配置只证明编译输入一致，不是固件签名或硬件运行认证。

## 首次安装：避开旧接收端收尾

当前已部署接收端仍有旧的 cache-off 风险与永久 halt 配置。新候选里的修复不能提前保护由旧程序执行的 OTA_END，因此首次安装使用独立 ROM 流程。

新增 `tools/bootstrap_ota_on_pi.py` 和 `tools/_mixlib/ota_bootstrap.py`：

1. 独立授权的无写入资格测试：PREPARE／ENTER_BOOT、同一芯片 USB-OTG ROM、完整读回、官方 watchdog reset 退出、返回旧镜像并通过心跳。
2. 独立安装任务：新鲜 8 MiB 备份、精确旧镜像／rollback bootloader／布局／安全标志核实，只写 B 槽并完整读回。
3. 提交前再次比较整片，确认 A 槽及所有共享区域未变。之后只写非活动的一个 4 KiB otadata 扇区，状态 NEW；保留活动记录。序号从实时合法记录推导，不硬编码历史 seq9/seq6。
4. 最终整片读回通过后，安装任务结束，**不自行重刷或循环 reset**。另一个明确授权的 boot-only 任务核实写入任务停止、保存读回与实机内容一致，才执行一次官方 watchdog reset。
5. 返回候选后核实实际文件 SHA、ELF、槽位、VALID 和持续心跳。

仅接受已验证的 0x800 USB-OTG 写入粒度。0x4000 粒度不适合一个 4 KiB 元数据扇区时立即拒绝，不能向邻接分区填充。资格凭据、写入和复位均是一次性持久 claim；超时后保留证据，不能换任务 ID 盲目重试。

首次安装 worker 的审批包、受保护目录与任务监管需要独立部署。它不是普通 apply 的自动失败回退，也不会未经批准从正常 OTA 切入 ROM。

2026-09-16 后续主机校验修复要求历史构建收据将旧 bootloader、有效配置、源码归档和构建日志精确绑定，并由已固定哈希的原始迁移收据提供独立来源。实际旧迁移收据没有这项记录，因此默认历史构建路径仍在停服和设备访问前拒绝；给当前配置文件重新计算哈希或补造 JSON 不能解除。另有显式 `mixos-reviewed-bootloader-binary-evidence/v1` 路径，校验固定旧／参考二进制、参考 ELF／配置及六份原始审计报告，精确解释 41 个差异字节并重新计算 48 个函数范围的哈希。它仅允许 `qualify-current-a-no-write`，不能授权安装 B 或 boot-only，也不自动降级采用。旧看门狗为名义 9 秒，参考值为 30 秒，二者不是完整行为等价；历史配置仍未恢复，候选接管之前的完整启动预算仍未证明，不夹带重刷 bootloader。

主机应用串口通过稳定 by-id 路径和实时物理身份核对后仅显式设置 DTR，不发 RTS 复位序列。只有 HELLO 接受前的传输失败可在总时限内有限重新打开；身份、健康或已接受 HELLO 后的故障立即拒绝。服务监管在同一维护锁内保存原状态，ROM 操作失败且未证明应用健康时保持停服；服务 active 不算固件健康证明。
