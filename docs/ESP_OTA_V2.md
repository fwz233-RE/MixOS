# ESP32 A/B 更新实现

本页描述第二版应用更新的结构和安全条件。命令用法见 [日常更新](ESP_OTA.md)，字节格式见 [更新协议](../protocol/OTA_V2.md)。

## 模块与存储

- `mix_ota.c`：应用写入、镜像校验、精确文件测量和 IDF OTA API。
- `mix_ota_tx.c`：单一 Flash 工作任务、事务状态、NVS 摘要与健康确认。
- `mix_link.c`：USB 协议、会话生命周期、队列和维护请求。
- `mix_health.c` 与 `mix_restart.c`：本地运行进度、看门狗协调和重启路径。
- `tools/ota_v2.py`：主机协议与严格运行核验。
- `tools/mixos_esp_update.py`：Linux 维护锁、systemd 任务、服务恢复与持久结果。

应用槽由分区表定义；普通更新不更改 bootloader、分区表、字体或 phy。事务摘要使用独立 NVS 命名空间，保留其他设置。RTC 记录仅供诊断，不是断电持久存储或启动授权依据。

## 更新事务

事务绑定随机 ID、完整应用文件 SHA-256、精确长度与目标槽。链路 epoch、维护 session、MCU 启动 ID 和事务 ID 分别表示不同身份，不能互相代替。

处理阶段包括接收、校验、准备提交、启动槽已选择、已请求重启、新应用待确认和已确认，并保留失败、中止或主机观察未知的结果。

- BEGIN 建立接收；ACK 只确认实际接收进度，不代表镜像已经提交。
- END 执行传输摘要、IDF 镜像验证和精确 Flash 文件测量，然后选择启动槽。
- QUERY 查询同一事务状态；日志不是正在运行镜像的独立证明。
- REBOOT 与 END 分离，并绑定源启动。重复请求具有幂等语义，不应重复结束句柄、提交或复位新应用。
- 运行身份测量另用 VERIFY_RUNNING，不能被旧 DONE、QUERY 或心跳替代。

主机允许按已知接收偏移对账，并在满足原事务与阶段约束时发送幂等控制请求；这与开始一个新的刷写任务不同。跨 MCU 重启的接收断点续传不在当前实现范围内。

NVS 记录与 otadata 不能原子提交。重启后必须结合日志、实际启动选择、镜像身份与状态核实结果；任何歧义都不能变成盲目重刷的依据。

## 试运行与健康确认

候选必须完成本地首帧提交、持续扫描、任务进度及 USB 维护往返。主机先核对完整文件、ELF、长度、槽位和本次启动身份，再用 HEALTH_ACK 回送固件挑战。

固件在连续本地和链路健康条件满足后调用 IDF 标记有效，并复读实际 VALID 状态。只有两步均成功才认为已确认。链路或维护会话变化、错误确认等会撤销临时维护证明；主机缺席本身不等于本地固件崩溃，也不会伪造确认。

主机随后还需观察持续心跳和新的完整身份测量，最后协调服务恢复与结果持久化。

## 有界只读重测

`verify_actual()` 单次 VERIFY_RUNNING 的预算不超过 5 秒，并受调用方原绝对截止时间约束。整次确认最多增加两次请求，条件包括：

- 原请求已经完整发送，异常发生在等待回复阶段。
- 请求 ID、epoch 与 session 证据明确，会话未改变。
- 等待期间有新增且新鲜的心跳。
- 没有新增解码错误或畸形回复。

重测使用新请求 ID，仍绑定同一启动和完整文件。发送失败、断连、身份变化或证据不足均停止；CAPS 与 HEALTH_ACK 不因此重试，也不新增 BEGIN／END／REBOOT。

`diagnostics.verification` 保存次数、超时、重测关联及停止原因。心跳窗口出现超限间隔后，只能重新形成后续连续窗口，不能借用之前的时间凑够成功条件。

## USB 与显示

短 DTR 断连需要锁存到主线程撤销旧会话；跨队列切代要保留新 HELLO；半帧发送恢复前需可靠发送零分隔符。正常 OTA 重启在软件复位前显式断开 USB，以便主机重新枚举。

显示配置保留 PSRAM 指令／只读数据访问方案，关闭 LCD RGB／GDMA 的 cache-off 中断选项，避免缓存不可用时读取 PSRAM 帧缓冲。双帧缓冲、屏幕时序和共享引脚约束仍属于硬件适配条件。

## Linux 执行与持久结果

主机先保存任务，再取得跨 USB 重枚举有效的维护锁，记录并停止服务，核实停止后才打开 CDC。实时 sysfs 身份通过后设置通信所需 DTR，不发送下载模式 RTS 复位脉冲。

每个任务保存不可变运行器与发布包快照；身份摘要防止意外漂移，但不是数字签名。固件、服务和记录持久化分别记录，只有全部成功才返回退出码 0。服务恢复失败不能被固件成功掩盖。

USB 协议的 CRC 与请求身份校验不构成密码学认证，串口权限和管理员的操作授权仍是安全边界。

## 首次安装

首次安全接收端安装与普通 apply 分开。相关入口为 `tools/bootstrap_ota_on_pi.py` 及配套审批、安装和观察工具，使用固定来源和明确授权，不是自动降级路径。

基本顺序为：无写入应用→ROM→应用资格检查，核对布局和安全标志，保存完整备份，只写非运行候选并读回，更新单个非活动 otadata 记录为 NEW，再单独核实启动及健康。

写入粒度必须能覆盖且仅覆盖授权区域。历史证据不足、身份不连续、共享区域改变或候选来源不明时拒绝；不得补造报告或扩大写入来绕过检查。

## 恢复边界

A/B 回退依赖再次启动。看门狗、panic 重启和最小 USB 维护模式能覆盖部分软件故障，但不能证明任意卡死可恢复。已 VALID 的版本发生后续运行故障，不保证自动换槽。

任务看门狗监视应用 MAIN、CDC I/O 和 OTA 工作任务，并不直接监视 TinyUSB 内部任务。SDK 低层重启有自身保护，仍不能用源码配置替代真实时序与故障测试。

完全失去应用与 USB 响应的恢复需要独立 EN／BOOT 控制或人工操作。故障镜像与断电测试应在备用板或具备独立恢复通道的条件下单独批准。
